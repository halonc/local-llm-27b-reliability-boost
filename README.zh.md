# 给本地 27B 装上"可靠性外挂"：数学从 92.7% 准确率到数学不再出错！

> 一台单卡 AMD R9700 32 GB 的 GPU 跑 27B 的 3-bit 量化模型，在需要精度的地方偶尔还是会翻车。本文记录：为什么换回 27B、它弱点在哪、怎么把计算从模型里剥出去、以及 27 道曾经必错的题最后修好了 26 道。

![封面](https://blog-eudc.infocused.cc/content/images/2026/10/cover-1280x720-1.png)

## TL;DR

| 指标 | 结果 |
|---|---|
| 换回 27B 3-bit 的理由 | 200K 冷读快 1.9 倍、缓存命中快 16.7 倍、4 路并发聚合吞吐高 11.1 倍；同一套 20 题的正误与 QFN **逐组相同** |
| 27B 的原始水平 | 日常 110 题 **92.7%**、高等数学 70 题 **75.7%** |
| 出错根因 | 26 道错题里 **零道是算术错**，全是公式、语义、单位链、边界 |
| 修复方式 | 计算全部外挂到常驻 `calc` 服务 + 把纪律写进 chat template |
| 最终结果 | 27 道必错题 **修复 26 道（96%）**，工具调用率 **27/27** |

## 1. 为什么从 QFN 换回 Paiton 27B 3-bit

前一阵子，我们把 8080 端口的主力模型换成了 **Qwen3.8-Flash-Next**（下文简称 **QFN**）——一个 MoE 模型，IQ3_XXS 量化，跑在 Strata 引擎上。理由很直觉：参数多、知识面广。

用了一阵子，体感是"稍微聪明一点点"，但和 [Paiton 的 27B](https://github.com/Eliovp-BV/paiton-vllm-plugin/blob/main/models/Qwen3.8-MXFP4-DFlash2/README.md)（W3A4）相比，**速度和并发回不去了**。

为了不凭感觉下判断，我们做了一次同题对照：20 道题，覆盖 200K 长文、工程识图、4 路并发、工程计算、代码、结构化输出，两边同 prompt、同 max_tokens、thinking 全关。

### 1.1 快在哪

| 指标 | QFN (IQ3_XXS) | **Paiton 27B (W3A4)** | 倍数 |
|---|---|---|---|
| 200K 冷读 TTFT | 176.3 s | **91.3 s** | 1.9× |
| 200K 第二次（缓存命中） | 28.4 s | **1.7 s** | **16.7×** |
| 4 路并发墙钟 | 36.8 s | **4.3 s** | 8.6× |
| 4 路并发聚合吞吐 | 9.7 tok/s | **107.6 tok/s** | **11.1×** |
| 20 题总耗时 | 5.7 min | **2.3 min** | 2.5× |

最能说明问题的是并发那一行：QFN 的 4 条请求 TTFT 分别是 **0.7 / 8.4 / 17.6 / 25.4 秒**——第 4 条要等 25 秒才出第一个字，本质是**排队**；Paiton 27B 的 4 条是 0.1 / 0.6 / 0.6 / 0.7 秒，**真并发**。

对一个"边跑 agent 边聊天"的用法，这个差距不是体感问题，是能不能用的分界线。

### 1.2 3-bit 够不够强

这是换回的关键疑虑：把 QFN 换成 27B，还压到 3-bit，能力会不会掉。

同一套 20 题，逐组对照：

| 组 | QFN | **Paiton 27B (W3A4)** |
|---|---|---|
| 200K 长文（3 题） | 3/3 | 3/3 |
| 工程识图（6 题） | 6/6 | 6/6 |
| 4 路并发（4 题） | 4/4 | 4/4 |
| 工程计算（3 题） | 2/3 | 2/3 |
| 代码（2 题） | 0/2 | 0/2 |
| 结构化（2 题） | 1/2 | 1/2 |
| **人工复核** | 19/20 | 18/20 |

**逐组数字完全相同。** 代码和结构化那两组的 0/2、1/2 是判分过严（关键词匹配），人工看实际都做对了。

换句话说：在这个任务分布上，QFN 没有体现出优势，而 Paiton 27B 快了一个数量级。这就是换回的底气。

### 1.3 换回之后的新问题

Paiton 27B 的绝对水平：**日常 110 题 102/110（92.7%）、高等数学 70 题 53/70（75.7%）**。

看起来还行，但错的那些非常致命——因为工程场景里，**一个数字错就等于全错**：

| 题 | 正确答案 | 模型给的 | 差 |
|---|---|---|---|
| H 型钢每米重量（119.8 cm²） | 94.0 kg/m | **28.1** | 3.3 倍 |
| 模板一次投入量 | 417.9 m² | **2010 m²**（把 1990 加错） | 加法错 |
| 会议纪要"本周五" | 10-23 | **10-24** | 差一天 |
| 3×3 行列式 | −3 | **0** | 完全不会 |
| 复数 (2+3i)(1−2i) 实部 | 8 | **−4** | 分配律符号错 |

这些错有个共同点：**它不是"理解不了"，而是"算错了"**。模型明明知道该用哪个公式，落在最后一步数字上翻车。

## 2. 诊断：26 道错题，零道是算术错

第一步是把"错在哪"量化。做法很笨但可靠：每道题的标准答案**由 Python 算**（不让模型自证），然后按类别统计。

### 2.1 一个反直觉的发现

原本以为"越难的运算越容易错"，数据推翻了它：

| 类别 | 正确率 |
|---|---|
| 长度 / 面积体积 / 重量换算 | **15/15 全对** |
| 百分比求值 / 反求 / 涨跌 / 折扣 / 税费 | **25/25 全对** |
| 功率电费 / 速度时间 / 密度质量 | **15/15 全对** |
| **小费分摊** | **2/5**（最差） |
| 温度换算 | 4/5 |
| 配比稀释 / 加权平均 / 复利 / 日期 | 各 4/5 |
| 高等数学 14 类 | 53/70 |

**"最简单"的小费分摊反而最差。** 因为它是复合运算（百分比 + 除法 + 四舍五入），错一步就全错。

### 2.2 26 道错题的真实原因

| 错法 | 例子 |
|---|---|
| **公式用错** | 加权平均算成简单平均；1:2:4 的砂用 2.4/3 而不是 2.4×2/7 |
| **语义理解偏** | "每人付多少"算成一堆别的组合 |
| **边界定义** | 日期差含不含首日；样本方差 vs 总体方差（n 还是 n−1） |
| **单位链** | 比例尺 45 m @ 1:1000 算成 45 cm（应 4.5 cm） |
| **符号/遗漏** | 负温度；链式法则漏乘；分配律符号 |

**没有一道是纯算术错。** 这个结论决定了方案方向。

## 3. 方案：把计算从模型里剥出去

摆在面前两条路：

1. 让模型**更会算**——换更大模型、加思考链、few-shot 提示
2. 让模型**根本不碰数字**——计算全部外挂

选第二条，理由很直接：**算术可以外包，公式不行**。而模型的错恰恰集中在公式和语义——这部分靠"更会算"解决不了，得靠"把公式固化"。

于是有了两层结构：

```
层 1  模型：读懂题，选「子命令 + 参数」        ← 不碰数字
层 2  calc：Decimal + sympy，算出全部数值      ← 不碰语义
```

一开始我分了三层（日常 / 高数 / 模板），后来发现**没有意义**——反正都要调 calc，只是子命令不同。压成两层后规则只剩一条：**选对子命令，别自己算**。

## 4. 实现：接口容错是真正的体力活

`calc` 是一个 Python 服务（systemd 常驻，sympy 只 import 一次）：

```bash
calc eval "4827+3916"                    # 8743
calc tip 240 20 3                        # 96.00
calc diff "x**2*exp(x)" --at 1           # 8.155
calc det "[[1,2,3],[4,5,6],[7,8,10]]"    # -3
calc stat "2,4,4,4,5,5,7,9" --ddof 0     # 方差 4.00
```

真正花时间的不是计算，是**模型传参的千奇百怪**。实测遇到的写法：

| 模型写法 | 处理 |
|---|---|
| `{"cmd":"add","argv":["4827","3916"]}` | 加 `add/sub/mul/div` 别名 |
| `eval "sqrt((3-6)^2+...)"` | 表达式支持 sqrt/abs/log/exp/sin/cos/pi，`^` 认作幂 |
| `det "[[1,2,3],[4,5,6]]"` | 矩阵接受 JSON 数组 / 分号 / 换行三种 |
| `integ "x^2+1" 0 2` | 积分接受位置参数 |
| `stat "3,5,7,9 std"` | 统计识别 std/variance/总体/样本，容忍多余词 |
| `binom 10 4 0.3` | 自动识别 n/p/k（不管顺序） |
| `wavg 80 90 70 3 2 1` | 自动判断"值组+权重组" |
| `solve "x**2-2*x-1=0"` | 自动去掉 `=0` |
| 参数写错 | 打印「参数错误 + 正确用法」，让模型自我纠正 |

这张清单是整篇文章里最可复用的部分——**任何给模型用的工具接口，都得假设调用方不按你的文档来**。

## 5. 其余四个短板，同一个思路

计算只是最痛的一个。语言模型还有四个通病，用同样的"外挂"处理：

| 短板 | 症状 | 做法 |
|---|---|---|
| **幻觉** | 编造不存在的路径、函数名、URL | `claim_verify`：从回答里抽断言，路径用 `ls`、函数用 `grep`、URL 用 `HEAD` 逐个核验，未通过的要求改口 |
| **长文中间丢失** | 200K 文档里中间段的事实常被漏 | `longdoc_scan`：按章节切块 + 关键词打分定位，先定位再精读 |
| **JSON 崩** | 少逗号、多解释、字段名变体 | `json_guard`：提取 → 修复（尾逗号/单引号/裸键）→ schema 校验 → 生成重试提示 |
| **不会说"不知道"** | 硬编一个格式正确的错答案 | 每轮注入当天日期 + "不确定就明说" + 收尾自检行 |

**诚实标注**：计算那部分是 27 题实测过的（0/27 → 26/27）；这四个只有"工具可用 + 设计合理"，**没做 A/B 量化**。

## 6. 注入：让它"自觉"用工具

工具做好了，模型不一定用。第一次实测：27 道题只有 9 道主动调工具。

解法是把纪律**写进 chat template**——不是写在提示词里让用户记得加，而是让模型每次请求的 system 里都有：

```jinja
{%- set CALC_RULE = "【计算纪律】凡涉及数值计算……必须调用 calc 工具，禁止心算。
拿到工具结果后立即给出最终答案，不要重复调用；收尾给出：自检：单位✓ 量级✓ 工具✓" %}
{{- "<|im_start|>system\n" + CALC_RULE + "<|im_end|>\n" }}
```

改模板而不是改客户端，好处是**对任何调用方生效**：不管来的 agent 是哪个、有没有传工具声明，模型收到的约束都一样。

验证方法很土：问它"你收到的系统提示里关于计算的规则是怎么写的"，它能一字不差背出来。

## 7. 部署：三样东西

```
docker-compose.yml          # 模型服务，端口不变
chat_template_calc.jinja    # 纪律写死在模板里
calc.service (systemd)      # 计算服务，sympy 常驻
```

走过的弯路：

- **加代理层**（模型前面套一个自动执行 tool_call 的 proxy）——能用，但违背"越简单越好"，拆了
- **改端口**（模型挪到 8090，proxy 占 8080）——所有客户端配置都要跟着改，拆了
- 最终回到**不改端口、不加中间层**，只改模板

`calc` 做成 systemd 而不是容器内进程，因为它要服务所有客户端（本机、NAS、NAS 里的容器），不该跟某一次模型容器的生命周期绑死。实测跨机调用 **42 ms**。

---

## 8. 踩过的坑

1. **`-e VAR=` 空串 ≠ 未设置**：ROCm 的设备变量写成空串会被判"零 GPU"，启动即崩，报错看起来像代码 bug
2. **每次新起 Python 付 350 ms 的 sympy import**：改成常驻服务后 540 ms → 42 ms
3. **模型把四则运算写成 `add`**：加别名之外，还得在工具描述里写"四则用 eval"
4. **模型拿到结果还再调一次**：模板加"直接作答，不要重复调用"
5. **判分取第一个数字**：答案里题面数字先出现，把 14.0 判成 −10 → 改成"任一数字命中即通过"
6. **全角减号 `−` 认不出**：`−1` 和 `-1` 是两个字符
7. **3×3 行列式两个都答 0**：模型根本不会展开，不是算错
8. **复数乘法分配律**：3i×(−2i) 算成 −6（应 +6）
9. **改端口/加代理都是弯路**：最后回到"不改端口"

## 10. 可复用的套路

如果要在别的模型上重复这件事：

1. **量化短板**：自建题库，标准答案由代码算，不让模型自证
2. **分类归因**：按类别统计正确率，找出"反直觉的差"（本例：小费最差、单位换算全对）
3. **接口固化**：把公式做成子命令，**并假设调用方不按文档来**
4. **注入强制**：写进 chat template，不依赖客户端自觉

**能外包的**：算术、单位换算、日期推算、矩阵/积分/统计
**不能外包的**：公式选择、题意识别、边界定义（含不含首日、样本还是总体）

后者只能靠"模板固化"——把每类题的公式写死，模型只填参数。
